# NINMODS — Project Rules & Engineering Standards (`docs/RULES.md`)

> **বাধ্যতামূলক নীতি (Mandatory Directive):** এই প্রোজেক্টে কাজ করার আগে যেকোনো এআই এজেন্ট (AI Agent) বা ডেভেলপারকে এই ডকুমেন্টের প্রতিটি ধারা শতভাগ মেনে চলতে হবে। কোনো কাজের শুরুতেই সম্পূর্ণ কোডবেস এন্ড-টু-এন্ড রিভিউ করতে হবে এবং বাস্তব ও পরীক্ষিত ফলাফল ছাড়া কোনো কাজ সম্পন্ন ঘোষণা করা যাবে না।

---

## ১. স্ট্যান্ডার্ড জাভাডক / ডক্সিজেন কমেন্টিং নীতি (Javadoc / Doxygen Style Comments ONLY)

* **ব্যানার ও ডেকোরেটিভ কমেন্ট সম্পূর্ণ নিষিদ্ধ (Zero ASCII Banners):**
  কোডের ভেতর কোনো প্রকার ব্যানার লাইন যেমন:
  ```java
  // =========================================================================
  // State Query Helpers (Restores state safely from Engine / Preferences)
  // =========================================================================
  // -------------------------------------------------------------------------
  /* ####################################################################### */
  ```
  লেখা সম্পূর্ণ নিষিদ্ধ।

* **স্ট্যান্ডার্ড ডকুমেন্টেশন স্টাইল (Official Javadoc / Doxygen Format):**
  প্রতিটি মেথড, ফাংশন, কনস্ট্রাক্টর ও ক্লাসের পূর্বে অফিসিয়াল জাভাডক (Java/Kotlin) বা ডক্সিজেন (C/C++) ফরম্যাটে কমেন্ট লিখতে হবে:
  ```java
  /**
   * Retrieves the stored or live toggle state of a feature.
   *
   * @param context Context used to resolve shared preferences.
   * @param featNum Native feature index.
   * @param featName Feature name or key.
   * @param defaultVal Default state if no prior state was saved.
   * @return Stored or live boolean state of the feature.
   */
  public boolean getToggleState(Context context, int featNum, String featName, boolean defaultVal) {
      // Implementation
  }
  ```
  - অবশ্যই `@param` দিয়ে প্রতিটি প্যারামিটারের উদ্দেশ্য ব্যাখ্যা করতে হবে।
  - অবশ্যই `@return` দিয়ে রিটার্ন ভ্যালুর ধরন ও তাৎপর্য ব্যাখ্যা করতে হবে।
  - যদি এক্সেপশন থ্রো করার সম্ভাবনা থাকে, তবে `@throws` উল্লেখ করতে হবে।

## ২. প্রতিটি ফাইলের প্যাকেজ ডিক্লারেশন ও ইমপোর্ট হেডার বাধ্যতামূলক অডিট নীতি (Mandatory Package & Import Header Audit)

* **কাজে হাত দেওয়ার আগে ও পরে ইমপোর্ট অডিট:**
  যেকোনো ফাইলে কাজ করার সময় বা কোড এডিট করার পূর্বে ও পরে, এজেন্টকে অবশ্যই ফাইলের সর্বপ্রথমে থাকা `package` নাম এবং প্রতিটি `import` স্টেটমেন্ট লাইন-বাই-লাইন পুঙ্খানুপুঙ্খভাবে মিলিয়ে দেখতে হবে।
* **কোনো প্যাকেজ হেডার বাদ দেওয়া সম্পূর্ণ নিষিদ্ধ:**
  জাভা বা কোটলিন ফাইলে কোনো অবস্থাতেই ফাইলের শুরুর প্যাকেজ ডিক্লারেশন (যেমন `package com.ninmods.main.menu;`) বাদ পড়া চলবে না। প্যাকেজ বাদ পড়লে ক্লাস ডিফল্ট প্যাকেজে চলে যায় এবং সম্পূর্ণ রেফারেন্স নষ্ট হয়।
* **প্রয়োজনীয় প্রতিটি ক্লাসের জন্য সঠিক ইমপোর্ট নিশ্চিত করা:**
  কোডে ব্যবহৃত প্রতিটি অ্যান্ড্রয়েড ফ্রেমওয়ার্ক ক্লাস বা উইজেটের জন্য প্রয়োজনীয় ইমপোর্ট নিশ্চিত করতে হবে, যাতে কোনো `cannot find symbol` বা কম্পাইলেশন এরর তৈরি না হয়।
* **অকেজো বা অনুপস্থিত ইমপোর্ট প্রতিরোধ:**
  কোনো ডুপ্লিকেট, অকেজো বা অনির্ভরযোগ্য ইমপোর্ট ফাইলে রাখা যাবে না।

## ৩. সব এজেন্টের জন্য বাধ্যতামূলক সম্পূর্ণ কোডবেস এন্ড-টু-এন্ড রিভিউ (Mandatory Full Code Review)

* **কাজে হাত দেওয়ার আগে সম্পূর্ণ কোড রিভিউ:**
  - যেকোনো এআই এজেন্টকে কোনো ফাইল এডিট করার পূর্বে সম্পূর্ণ সম্পর্কিত কোডবেস ম্যানুয়ালি রিভিউ করতে হবে।
  - বিচ্ছিন্ন কোনো ফাংশন বা লাইনে পরিবর্তন করে কাজ শেষ ঘোষণা করা সম্পূর্ণ নিষিদ্ধ।
  - **সম্পূর্ণ পাইপলাইনের ইন্টারকানেকশন ম্যাপিং (Trace the complete path):**
    `User Event / Floating Menu` ➔ `MenuController` ➔ `JNI Bridge (NativeBridge / MenuPreferences)` ➔ `C++ Engine (Client.cpp / NinliteProtocol)` ➔ `Root Daemon / Kernel Driver` ➔ `ESP / Aimbot Processing` ➔ `Overlay Rendering`
    এই সম্পূর্ণ ট্রানজিশন চেইন পুঙ্খানুপুঙ্খভাবে মিলিয়ে দেখতে হবে যাতে কোনো এক স্তরের পরিবর্তন অন্য কোনো স্তরে ব্রেক না ঘটায়।

## ৪. চ্যানেল আইসোলেশন ও কার্নেল/ডেমনের আচরণ (Strict RT/QX Isolation)

* `ninmods` এর সমস্ত মেমরি অপারেশন, ইএসপি এবং এইমবট **১০০% আসল কার্নেল ড্রাইভার (RT Ring-0 Character Device `/dev/BYNb`)** এর মাধ্যমে পরিচালিত হবে।
* `ninlite` হলো **Root Daemon IPC Engine Mode (QX)**, যা রুট ডেমন এবং `process_vm_readv` লিনাক্স সিসকল ব্যবহার করে পরিচালিত হয়। কোড পরিবর্তন করার সময় এই দুই চ্যানেলের আচরণ সবসময় কঠোরভাবে পৃথক রাখতে হবে। একটি চ্যানেল ফেইল করলে অন্য চ্যানেলে অটো-ফলব্যাক সম্পূর্ণ নিষিদ্ধ।

## ৫. মাস্টার সুইচ ও লবি মেমরি পজ প্রটোকল (Master ESP & Lobby Memory Gating)

* মেনুতে অবশ্যই একটি ডেডিকেটেড "ESP Master" সুইচ থাকবে (`FeatureCatalog.ESP_MASTER`, native ID 1)।
* লবিতে থাকাকালীন ব্যবহারকারী মাস্টার সুইচ বন্ধ করলে ডেমন ও ক্লায়েন্টে মেমরি স্ক্যানিং ও রেন্ডারিং সাথে সাথে বন্ধ হবে (`if (!Actived.activar) return;`)।
* মাস্টার সুইচ বন্ধ করলে সাব-ফিচারগুলোর সিলেক্টেড স্টেট (যেমন Box, Line, Distance) মুছে ফেলা যাবে না। ম্যাচ শুরু হওয়ার পর মাস্টার অন করলেই পূর্বের সিলেক্টেড ফিচারগুলো সাথে সাথে চালু হবে।

## ৬. স্থায়ী ৯০ অটো-ইনক্রিমেন্টাল ভার্সনিং প্রটোকল (Strict Permanent 90.X Versioning)

* মেজর ভার্সন **৯০ সর্বকালের জন্য ফিক্সড** (যেমন `V90.106` ➔ `V90.107` ➔ `V90.108`...)। এটি কখনো কোনো অবস্থাতেই পরিবর্তন করা যাবে না।
* প্রতি আপডেটে `app/src/main/res/values/version.xml`-এ `app_version` এবং `version_code` ক্রমানুসারে বাড়াতে হবে।
* রুট বা কোনো ডিরেক্টরিতে কোনো `.idsig` ফাইল থাকা সম্পূর্ণ নিষিদ্ধ (`apksigner`-এ `--v4-signing-enabled false` ব্যবহার করতে হবে)।

## ৭. ক্লাউড-ফার্স্ট বিল্ড ও পুশ প্রটোকল (Zero Local Builds / Zero Push Without Explicit Order)

* লোকাল মেশিনে কোনো ভারি গ্রেডল ডেমন বা NDK বিল্ড চালানো সম্পূর্ণ নিষিদ্ধ। সমস্ত বাইনারি ও APK ১০০% GitHub Actions ক্লাউড পাইপলাইনের মাধ্যমে তৈরি হবে।
* ব্যবহারকারী নিজে মুখে স্পষ্টভাবে "পুশ করো" বা "push" না বলা পর্যন্ত গিটহাবে কোড পুশ করা সম্পূর্ণ নিষিদ্ধ।
